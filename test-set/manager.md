## 2. 问题与裁判边界

### 2.1 资料约束

modEnv1使用 Minecraft 1.21.1 NeoForge，默认基础库 `D:/Minecraft/MKB-Database`。完整快照、737教程和灾变网页已由维护者构建。引擎在生成任何题目之前检查活动快照、Minecraft与加载器版本，以及两个必需网页来源是否已关联入库文档；不满足则退出，不消耗问答调用。该检查不证明教程内容完整，仍需审阅检索结果。不能用旧空库检查推定当前状态。

- 快照是当前游戏已安装身份和运行时规则的证据。
- `https://www.mcmod.cn/modpack/737.html` 是环境外整合包教程，不代表当前环境安装了该整合包或其魔改配方。
- `https://www.mcmod.cn/class/5214.html` 是环境外灾变网页，不得要求有本地灾变导出图片，也不得声称灾变已经安装。
- 同名对象必须重新核对资料范围。例如灾变焰魔与铁魔法Boss不能混为一谈。
- 各类别共用上下文是题集设计的一部分；类别之间重置。不能为使测试通过擅自拆成61个独立会话。
- Entity-08、Gameplay-14/15等依赖上文，不能单独执行后据此评判多轮能力。

Crafting包括制作与获取：工作台、酿造、锻造、功能方块加工、掉落、战利品箱、交易都可能相关。快照尚未导出某类数据或检索未覆盖时，应报告证据缺口，不能由评测标准给回答模型补充答案。

Crafting-01保留钻石剑问题，但钻石剑通常属于有序配方；不将“原版无序”作为该题硬断言，也不静默换成另一道题。实际配方类型以快照为准。

六位法师预期为 pyromancer、cryomancer、necromancer、archevoker、priest、apothecarist；两个Boss预期为 dead_king、fire_boss。当前本地语言文件将其标为“死者之王”和“提洛斯回响·原初受火者”，不能仅用“焰魔”关键词判定后者。参考身份来自现有模组版本及本地源代码，版本升级后应核对并修订题集版本，不把这些预期推广到所有版本。

### 2.2 双线裁判

1. **规则裁判**：本地Java确定性规则，不调用模型。检查异常、已选快照、引用、图片可用性、结构化实体状态、配方产物、资料范围及部分文本要点。
2. **人工裁判**：维护者逐轮填写S/A/B/C/D与自由评语，判断事实、完整性、上下文、战术可执行性、属性、图片视觉语义和体验。

题集的 `expected.answerPoints` 和 `judgeRubric` 是评审要点，不是给回答模型的额外证据；不得把它们塞入检索结果或系统提示词。Error-07的模组纠错必须由泛化的身份与来源解析实现，禁止在生产提示词加入该题的特例。

现有规则有限：例如配方产物和一张有效卡片不证明全部替代配方都展示了；“交易”关键词不证明交易细节正确；六张身份正确的法师图不证明六份属性正确。明确保留人工检查项，不通过脆弱关键词伪造全面验收。某些游戏属性或数据通道缺失也可能导致真实失败。

不启用额外LLM裁判，不将模型自评当成人工评级。规则PASS不能直接换算为S。

## 4. 执行问答：每套题一个入口脚本

从项目根目录运行：

```powershell
# 无模型、无凭据的题集规格检查
.\scripts\run-golden-set-modEnv1.ps1 -ValidateOnly

# 真实61轮问答；显式借用保存的Key；不运行额外模型裁判
.\scripts\run-golden-set-modEnv1.ps1 -UseSavedKey

# 指定已有基础库
.\scripts\run-golden-set-modEnv1.ps1 -UseSavedKey -DataDirectory D:\Minecraft\MKB-Database

# 限制本进程问答模型请求总数；上限写入本轮config.json
.\scripts\run-golden-set-modEnv1.ps1 -UseSavedKey -MaxModelRequests 488
```

先关闭占用同一基础库的软件实例。程序使用标准目录锁；锁冲突应退出，不得删除锁文件、强杀用户进程或并发打开H2。

脚本默认运行 `mvnw compile dependency:copy-dependencies` 准备当前代码和运行时依赖，不打包发行程序，不执行release构建。编译成功不代表问答正确。确认编译产物确实对应当前源码后可加 `-SkipCompile`。

脚本调用真实QaPipeline，`--repeat 1 --no-judge`；每个类别按题目顺序运行，同类共享一个会话，六个MultiStep组分别运行。使用 `maa.eval.outputRoot` 与 `maa.eval.runId` 将引擎产物直接放到本题集会话目录。引擎拒绝覆盖已有run目录。

正常完成生成原始档案和 `eval.md`，不生成本轮 `result.md`。发生问题时保留部分完成记录；若有已完成轮次，仍生成其人工模板。不能以部分结果冒充61轮通过。连一轮都未记录时不生成空白成功报告。

原归档不要覆盖。下一批开始前，已有 `eval.md` 会阻止新运行；确认旧评审需要留档后使用：

```powershell
.\scripts\run-golden-set-modEnv1.ps1 -UseSavedKey -ArchivePreviousReview
```

该参数保存旧评审和已有结果的备份，不是允许丢弃评语。已有result.md在备份哈希验证通过后从当前入口移除，避免被误认成本轮结果；历史提交文件和原答案不修改。新result.md仍需本轮人工确认后生成。

脚本不会重建基础库；QA正常的补检仍可能访问网页、更新公共资源缓存。不要把该运行等同完全离线测试。

## 5. Token与其他成本

- 61轮不等于61次模型调用。每轮可能包含分类、实体解析、检索规划、覆盖检查、最终回答，以及提供方/工作流重试；这些实际模型调用都会消耗Token。
- 当前正常配置模型的入口采用原生工具规划循环，每轮最多6次决策和一次最终回答；明确澄清或本地图片缺口可省略最终回答调用。旧兼容入口仍可能使用其他阶段。主问答模型关闭隐式自动重试；MaxModelRequests为可选的进程级硬上限，默认0不设上限，不修改保存设置。
- 类别连续会话会携带历史，上文越长后续输入量可能越大。这一设计与旧单题会话的成本不可直接比较。
- 默认不开启稳定性重复，不自动额外跑模型裁判，也不为“复核”偷偷重新生成答案。
- 页面与图片下载本身不是模型Token；会消耗网络时间及流量。默认本地ONNX嵌入不是云端回答API的Token。
- 自动规则、生成模板、解析人工评级和汇总结果不调用模型，不消耗模型Token。
- 后续让Agent阅读评语、检查证据、分析改进，会产生该Agent自身的模型用量；不意味着再次调用软件的问答API。
- 当提供方用量缺失时，报告必须保留“不完整用量”的限制，不能把未记录当作0。

Agent执行真实问答前，必须已有明确的保存凭据读取授权和本批次题量授权。脚本开关不是Agent绕过用户授权的手段；过去批次最多22题的授权不能直接扩展为本批61题。凭据不出现在命令参数值、日志、文档和测试产物中。

## 6. 人工填写 eval.md

模板按本轮实际记录生成，包含稳定题号、问题、规则结果和会话定位。规则详细输出在 `turns.jsonl` 与引擎机器报告中。

```markdown
## Entity-01

问题：……
规则结果（仅供参考）：PASS
会话：runs/<runId>/sessions/<sessionId>.json

人工评级：S

<!-- human-comment:begin -->

<!-- human-comment:end -->
```

评级定义：

| 评级 | 定义 |
| --- | --- |
| S | 通过、完全OK；无需评语 |
| A | 基本通过，轻微瑕疵；不改也可用，可给建议 |
| B | 略有问题，大部分有效、小部分不相关，仍需改进 |
| C | 存在问题，部分有效，很需要修改 |
| D | 严重问题，几乎无相关内容或给不出回答 |

只填“人工评级：S”即可，不强制为S编写理由。A–D也不在脚本层强制评语，但建议给出定位和改进方向。评级可以紧跟冒号或单独位于下一行。空白是未审阅，不是S。

所有自由文字写在对应 `human-comment` 标记之间；总体意见写在 `general-comment` 标记之间。标记之间可使用Markdown、粘贴句子、链接和任意评语，不要求固定语义格式。保留题号、run_id和标记，不用复制的规则结果决定最终统计；脚本以冻结的原始记录为准。

新增未执行题的人工段落、重复题号、错误runId、缺少评级、损坏标记都会拒绝汇总。未执行题不需要强行填D，在结果中单列未执行。

## 7. 提交并生成 result.md：每套题一个入口脚本

确认已审阅当前实际执行的全部轮次后运行：

```powershell
.\scripts\result-golden-set-modEnv1.ps1 -ConfirmReviewComplete
```

该显式参数是维护者确认完成评审的步骤。Agent不能仅因为文件修改过就自行加此参数；维护者说“评估完成，生成结果”等明确指令后才能提交。

脚本验证当前run身份、题集快照与原始逐题记录摘要、题号和评级完整性，保存人工原文和结构化结果，然后生成：

- 本轮身份与可比条件、执行状态及归档入口。
- 计划、实际、错误与未执行轮数。
- 规则PASS/FAIL及逐题对应。
- S/A/B/C/D分布、评审覆盖率、S+A的人工可用比例。
- 逐题对照、自由评语原文、性能与网络统计。
- 明显双线分歧列表，以及待Agent完善的分析章节。

已提交run再次提交会被拒绝，不静默覆盖。若确需修正人工评级，先由维护者明确指定归档修订方案；不要删掉history来绕过保护。修复代码后必须新建run重新生成，不能修改旧答案冒充修复后的输出。

原始JSONL不可信或截断时，汇总应报错，不应忽略坏行。缺失用量、网络细项或原始状态时保留未知，不能伪造零成本和全量完成。

## 8. Agent完善结果

维护者授权分析后，Agent读取当前 `eval.md`、脚本生成的 `result.md`、相关逐题原始记录，并按需查看图片与证据，不需要再次运行题集。

1. 分析**全部**人工评语，不能只看自动列出的“PASS对C/D、FAIL对S/A”。规则通过但人工B也可能有重要问题。
2. 双线分歧：区分生产实现、资料缺失、题目歧义、断言过严/过宽、人工与机器检查范围不同。
3. 上版比较：按相同问题和同一规则的交集比较；将题集、规则、基础库、模型、缓存及会话策略变化单列。没有可比上版时明确首轮，不编造增幅。
4. 改进方案：列出问题、原题号与证据、优先级、预计修改、验证方法和仍未确认的部分。
5. 保留人工评级与评语原文，不把B自动改为A，不把规则修订后的重判冒充模型重测。
6. 完善当前 `result.md` 后，将补充版本另存为 `history/<runId>/result-agent.md`，保留脚本汇总原稿。注明分析时间、依据和未实际验证的推断。

本轮维护者明确要求人工D全部判为FAIL，报告因此增加“原始规则／复核规则／人工”三列，并保存`reviewed-rule-decisions.json`。此为人工复核否决，不能冒充自动裁判已修复；原始JSONL与脚本历史原稿不改。未来修订自动断言须另存规则版本与旧答案重判结果，新问答则新建run，三种结果分别统计。

不把新方案当作已经实现；不把测试通过当作游戏事实全面正确；不把摘要文件当作完整会话备份。

## 9. 可复用与边界

`run-golden-set-modEnv1.ps1` 和 `result-golden-set-modEnv1.ps1` 是该题集的两个入口，公共的无模型读写/汇总逻辑在 `scripts/test-set-tools.ps1`。未来modEnv2建立独立题集与两个入口，复用公共逻辑，不能共用active-run或覆盖modEnv1历史。
